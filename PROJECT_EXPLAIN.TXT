1. PROJECT EXECUTIVE OVERVIEW
================================================================================
Ironclad Gaming Sanctuary is an esports gaming lounge and cafe management 
platform. It was originally forged for an elite gaming lounge located at:
  Behind Redtape Showroom, Near PSPCL Office, Guru Angad Dev Nagar,
  Sri Muktsar Sahib, Punjab – 152026.

The platform has been completely generalized and white-labeled so that any 
gaming cafe owner anywhere in the world can run, rebrand, and customize the 
entire application directly from the web-based Administrator Panel without 
editing any source code.

KEY OBJECTIVES DELIVERED:
- Provide customers with real-time seat availability and frictionless online booking.
- Prevent double bookings with zero race conditions (including late-night sessions).
- Enable seamless Indian UPI payments (GPay, PhonePe, Paytm, BHIM) with automated QR.
- Generate high-impact 1-page printable passes and instant downloadable PDFs.
- Enable instant WhatsApp messaging with deep links and delivery status tracking.
- Allow owners to customize Cafe Name, Logo, Tour Video, Hero Headlines, Address,
  and Amenities in real time.
- Present gamer-friendly hospitality policies: 4K + QLED screens, cozy aesthetic 
  ambience, in-house chilled beverages/packed food, and 100% outside food allowed.

3. DATABASE SCHEMA & DATA RELATIONSHIPS
================================================================================
The relational schema `ironclad_gaming` consists of 13 primary tables:

1. `admins`:
   - id, username, password_hash, full_name, email, role (admin/manager), 
     is_active, last_login, created_at.
   - Purpose: Secure administrative access control.

2. `station_categories`:
   - id, name, slug, description, icon, display_order, is_active, created_at.
   - Purpose: Grouping gaming stations (e.g. Esports PC, PS5 Console Lounge).

3. `stations`:
   - id, category_id, name, code (e.g. ST-PC-01), specs, hourly_rate, 
     status (active/maintenance/inactive), display_order, created_at.
   - Purpose: Individual hardware inventory tracking.

4. `customers`:
   - id, full_name, phone, email, notes, created_at, updated_at.
   - Purpose: Gamer registry; phone number acts as primary customer lookup key.

5. `bookings`:
   - id, booking_ref (e.g. IC-2026-BTT36), customer_id, station_id, 
     booking_date, start_time, end_time, duration_hours, booking_type (online/walkin),
     status (pending/confirmed/in_session/completed/cancelled),
     reschedule_status (none/pending/approved/rejected), requested_date, requested_time,
     total_amount, discount_amount, final_amount, promo_code, notes,
     whatsapp_status (pending/sent), whatsapp_sent_at, created_at, updated_at.
   - Purpose: Master session record with atomic state tracking.

6. `payments`:
   - id, booking_id, customer_id, payment_method (upi_qr/cash/card),
     upi_transaction_id, screenshot_path, amount,
     status (pending/verified/rejected), admin_notes, verified_by, verified_at, created_at.
   - Purpose: Audit trail of all financial inflows and transaction proofs.

7. `pricing_plans`:
   - id, title, duration_hours, price, original_price, badge, 
     features_json, is_popular, is_active, display_order, created_at.
   - Purpose: Multi-hour battle pass packages.

8. `offers`:
   - id, promo_code, title, discount_type (flat/percent), discount_value,
     min_booking_amount, valid_from, valid_until, usage_limit, times_used, is_active.
   - Purpose: Marketing promo campaigns.

9. `reviews`:
   - id, customer_name, rating (1-5), review_text, game_played,
     is_approved, is_featured, created_at.
   - Purpose: Social proof & community feedback.

10. `gallery_images`:
    - id, title, caption, file_path, poster_path, media_type (image/video),
      category (pc_arena/console_lounge/tournaments/rgb_vibes),
      is_featured, display_order, created_at.
    - Purpose: Visual arena showcase and 4K gameplay reels.

11. `operating_hours`:
    - id, day_of_week (0-6), open_time, close_time, is_closed.
    - Purpose: Cafe operating schedules (Default: 10:00 AM – 11:00 PM daily).

12. `activity_logs`:
    - id, admin_id, action, description, ip_address, user_agent, created_at.
    - Purpose: Immutable administrative audit trail.

13. `site_settings`:
    - setting_key (PRIMARY KEY), setting_value, setting_group, updated_at.
    - Purpose: Central key-value store powering the white-label branding engine.

5. PROBLEMS ENCOUNTERED DURING DEVELOPMENT & HOW WE SOLVED THEM
================================================================================

--------------------------------------------------------------------------------
5.1. THE MIDNIGHT-CROSSING DOUBLE-BOOKING BUG
--------------------------------------------------------------------------------
THE PROBLEM:
When testing session bookings late in the evening (e.g. 10:03 PM for a 2-hour 
session), the session end time calculated to 12:03 AM (represented as `'00:03:00'` 
in 24-hour time).
Because the existing collision detection checked:
  `WHERE start_time < :end_time AND end_time > :start_time`
Lexicographically in SQL and PHP, `'00:03:00' < '22:03:00'` evaluated to FALSE!
As a result:
- The system falsely concluded that the session did NOT cross or overlap.
- The closing time check (`end_time > '23:00:00'`) failed to detect closing violations.
- A second customer was able to book the exact same station at 9:59 PM – 10:59 PM,
  causing a critical double-booking collision on the same PC rig!

HOW WE SOLVED IT:
1. Replaced all naive 24-hour time string comparisons with absolute `DATETIME` 
   ranges combining `booking_date` and `time`.
2. When `end_time <= start_time`, the algorithm automatically detects that the session 
   crosses midnight into the subsequent calendar day (`DATE_ADD(booking_date, INTERVAL 1 DAY)`).
3. The collision detection SQL query in `is_slot_available()` was upgraded to:
     `TIMESTAMP(b.booking_date, b.start_time) < :end_dt AND`
     `IF(b.end_time <= b.start_time,`
     `   TIMESTAMP(DATE_ADD(b.booking_date, INTERVAL 1 DAY), b.end_time),`
     `   TIMESTAMP(b.booking_date, b.end_time)) > :start_dt`
4. Upgraded the same logic in `get_live_arena_status()` and `get_station_schedule_matrix()`.
5. Created a comprehensive automated test suite with 52 test scenarios covering 
   same-day overlaps, midnight crossings, next-day overlaps, and boundary slots. 
   All 52 tests passed cleanly with zero collisions allowed.

--------------------------------------------------------------------------------
5.2. SQLSTATE[HY093] PREPARED STATEMENT PARAMETER BINDING ERROR
--------------------------------------------------------------------------------
THE PROBLEM:
When walk-in sessions were created at the counter or payments were verified, the 
system threw a fatal exception:
  `SQLSTATE[HY093]: Invalid parameter number`
The query in question was:
  `INSERT INTO payments (..., status, ..., verified_at) VALUES (..., :pst, ..., IF(:pst = 'verified', NOW(), NULL))`
In PHP PDO, when native prepared statements are active (`PDO::ATTR_EMULATE_PREPARES => false`), 
MySQL does not allow the same named parameter placeholder (`:pst`) to be referenced 
multiple times in a single query unless emulation is turned on. When PDO bound the array, 
MySQL detected a mismatch between the number of placeholders and bound parameters.

HOW WE SOLVED IT:
1. Computed the verified timestamp in PHP beforehand:
   `$verified_at = ($payment_status === 'verified') ? date('Y-m-d H:i:s') : null;`
2. Used unique named placeholders for every column:
   `VALUES (..., :pst, ..., :vat)`
3. Bound `:pst => $payment_status` and `:vat => $verified_at` cleanly.
4. Resolved the exact same pattern in `admin/booking-detail.php` by dynamically 
   constructing the update clause with unique placeholders.

--------------------------------------------------------------------------------
5.3. MULTI-PAGE RECEIPT PRINT SPILLOVER
--------------------------------------------------------------------------------
THE PROBLEM:
When users clicked "Print Pass" or printed via browser dialog, the receipt was 
spilling onto a second page. The bottom verification QR code, guidelines, and 
signature stamp were pushed onto page 2, wasting paper and producing an 
unprofessional, broken pass.

HOW WE SOLVED IT:
1. Implemented a strict print media stylesheet:
   `@page { size: A4 portrait; margin: 8mm 10mm; }`
   `@media print { .receipt-wrapper { page-break-inside: avoid !important; } }`
2. Compacted the layout into high-efficiency flexbox and CSS grid structures:
   - Header with inline logo, title, and receipt metadata.
   - Status ribbon with single-line reference number and pill badge.
   - Two-column info grid for gamer details and hardware allocation.
   - Tightened table row padding to `6px 10px`.
   - Placed the scannable QR code and counter digital stamp side-by-side in the footer.
3. Integrated `html2pdf.js` so customers can download a pixel-perfect, 
   1-page A4 PDF file directly to their phone with a single tap.

--------------------------------------------------------------------------------
5.4. CUSTOMER NAME CASE INCONSISTENCY
--------------------------------------------------------------------------------
THE PROBLEM:
Customers and staff frequently entered names in all-lowercase (e.g. "shubhdeep singh") 
or erratic casing. This appeared on official receipts, PDF passes, admin dashboards, 
and WhatsApp messages as unprofessional data.

HOW WE SOLVED IT:
1. Created a dedicated UTF-8 aware helper function in `includes/functions.php`:
   `function to_title_case(string $name): string`
   It trims excess whitespace, normalizes multiple spaces, converts to lowercase, 
   and applies `mb_convert_case(..., MB_CASE_TITLE, 'UTF-8')`.
   Example: `"shubhdeep singh"` -> `"Shubhdeep Singh"`.
2. Applied `to_title_case()` across all entry points:
   - Online booking form (`book.php`)
   - Admin walk-in creation (`admin/booking-create.php`)
   - Review submission (`reviews.php`)
   - Customer profile updates (`admin/customers.php`)
3. Executed an automated database migration script that converted all existing 
   customer records in the database to Title Case.

--------------------------------------------------------------------------------
5.5. LANDING PAGE VIDEO CLUTTER & PAGE WEIGHT
--------------------------------------------------------------------------------
THE PROBLEM:
Earlier iterations featured multiple heavy video players embedded directly inside 
the homepage: one in the hero box, one full-width walkthrough section in the middle 
of the page, and one in a modal. This caused:
- High page loading times and heavy mobile data consumption.
- A cluttered user experience with redundant video players.
- User feedback explicitly requested: "DO NOT ADD VEDIO TO MUCH TIME ON LANDING PAGE" 
  and "WATCH ARENA TOUR IS LESS VISIBLE".

HOW WE SOLVED IT:
1. Removed the redundant full-width embedded `<video>` section from the middle of 
   the landing page.
2. Removed redundant small video pills from the logo box.
3. Created exactly ONE prominent, high-visibility CTA button in the hero section:
   `<button class="btn btn-iron btn-iron-cyan btn-tour-hero">`
   Styled with cyan neon illumination, an animated play icon, and a "4K VIDEO" badge.
4. When clicked, it opens a focused, high-speed Bootstrap modal (`#arenaTourModal`) 
   with playback controls and automatic pause on dismissal.

--------------------------------------------------------------------------------
5.6. HARDCODED BRAND IDENTITY DECOUPLING
--------------------------------------------------------------------------------
THE PROBLEM:
The codebase originally contained hardcoded references to "IRONCLAD GAMING SANCTUARY", 
"NOBG_IRONCLADLOGO.png", "Sri Muktsar Sahib", and specific street addresses across 
more than 15 PHP files, footer templates, and WhatsApp strings. Changing cafe details 
required manual file editing across the entire codebase.

HOW WE SOLVED IT:
1. Created the `site_settings` table in MariaDB to hold branding configuration.
2. Added cached helper functions (`get_brand_name()`, `get_brand_short()`, 
   `get_brand_logo()`, `get_brand_video()`, `get_brand_address()`, etc.).
3. Replaced all hardcoded text across `index.php`, `about.php`, `contact.php`, 
   `pricing.php`, `experiences.php`, `receipt.php`, `footer.php`, `header.php`, 
   and WhatsApp generator with dynamic helper calls.
4. Rebuilt `admin/settings.php` as a complete White-Label Branding Center with 
   multipart file upload handling for live logo and video replacements.
5. Verified live switching via automated test (`test_white_label.php`).

--------------------------------------------------------------------------------

   - Cozy & Aesthetic Ambience

5.8. SESSION & CONFIG LOADING ORDER IN PUBLIC VIEWS

THE PROBLEM:
When moving to dynamic helpers, some public views called `get_brand_name()` on line 7 
before requiring `includes/header.php` on line 19. Because `config/config.php` and 
`functions.php` were only loaded inside `header.php`, PHP threw a fatal error: 
`Call to undefined function get_brand_name()`.

HOW WE SOLVED IT:
1. Standardized all public pages (`index.php`, `about.php`, `contact.php`, `pricing.php`, 
   `experiences.php`, `book.php`, `reviews.php`, `gallery.php`, `offers.php`) to 
   start with:
   `require_once __DIR__ . '/config/config.php';`
2. `config.php` acts as the master entrypoint: it initializes session security, 
   sets timezone, loads `database.php`, and loads `functions.php`.
3. Tested all pages via automated HTTP fetch script; 100% of pages returned HTTP 200 
   with zero errors.

6. SECURITY & RELIABILITY IMPLEMENTATION
================================================================================
1. CROSS-SITE SCRIPTING (XSS) DEFENSE:
   - Centralized output escaping function `e($string)` using `htmlspecialchars()` 
     with `ENT_QUOTES` and UTF-8 encoding applied to all customer inputs.

2. SQL INJECTION IMMUNITY:
   - 100% of database queries use PDO prepared statements with bound parameters. 
     No dynamic variable interpolation in SQL statements.

3. CROSS-SITE REQUEST FORGERY (CSRF) TOKENS:
   - Cryptographic random token generated per session (`csrf_token()`).
   - Every administrative form, booking form, review submission, and contact form 
     verifies `verify_csrf()` before processing POST data.

4. ADMINISTRATIVE ACCESS GATING:
   - `require_admin()` enforces authentication on every script in `/admin/`.
   - Unauthenticated requests are immediately halted and redirected to `/admin/login.php`.
   - Passwords hashed using standard `password_hash($pass, PASSWORD_DEFAULT)`.

5. SECURE FILE UPLOADS:
   - `handle_file_upload()` validates both file extensions and strict MIME types 
     (e.g. `image/png`, `video/mp4`).
   - Uploads are saved with unique randomized prefixes into isolated subfolders 
     (`uploads/branding/`, `uploads/gallery/`, `uploads/qr/`).
   - Direct PHP script execution disabled in upload paths.

6. AUDIT TRAIL LOGGING:
   - Every sensitive administrative event (payment verification, booking cancellation, 
     slot reschedule, white-label update) is recorded in `activity_logs` with admin ID, 
     timestamp, IP address, and user agent.
